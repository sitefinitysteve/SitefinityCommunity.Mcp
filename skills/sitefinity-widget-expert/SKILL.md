## Controller Structure

Every widget controller requires these attributes:

```csharp
[EnhanceViewEnginesAttribute]  // Required - Feather view discovery across assemblies
[ControllerToolboxItem(Name = "MyWidget", Title = "My Widget", SectionName = "ContentToolboxSection", CssClass = "sfListitemsIcn sfMvcIcn")]
public class MyWidgetController : Controller
```

- `[EnhanceViewEnginesAttribute]` is mandatory for Sitefinity to find views
- `[ControllerToolboxItem]` registers the widget in the page editor toolbox; discovery is automatic (no Global.asax registration)
- `CssClass` should combine a specific icon class with `sfMvcIcn` (the blue MVC badge): `sfListitemsIcn`, `sfVideoIcn`, `sfImageViewIcn`, `sfFormsIcn`, `sfNavigationIcn`, `sfNewsViewIcn`, ...
- Controllers inherit from `System.Web.Mvc.Controller` directly (no Sitefinity base class required)

### Search indexing: [IndexRenderMode] and index-mode detection

Sitefinity's Lucene search indexer builds the index by RENDERING each page server-side and crawling the output. Every widget therefore participates in search indexing by default - which is right for content widgets and wrong for anything personalized, session-dependent, expensive, or noisy (login boxes, dashboards, "hello {user}" headers, filter UIs). Two tools control this:

- **`[IndexRenderMode(IndexRenderModes.NoOutput)]`** on the controller class (namespace `Telerik.Sitefinity.Web.UI`; the enum has exactly two members, `Normal` and `NoOutput`) - the widget renders NOTHING during an index pass, so none of its output pollutes the page's search entry. Use it whenever the widget's output should not be searchable.
- **Detect index mode at runtime** when only PART of the rendering should change: the indexer flags the request with `Page.Items["IsInIndexMode"]` (set by `InMemoryPageRender` during the crawl; `SitefinityPage` and the `Control.IsInIndexMode()` extension read the same key). Check `HttpContext.Current?.Items != null && SystemManager.CurrentHttpContext?.Handler is Page page && page.Items["IsInIndexMode"] is bool inIndex && inIndex` (wrap it in a small helper). Typical use: a JS-rendered widget emits plain crawlable HTML during indexing and its normal client mount point otherwise - the `sitefinity-vue3-vite8-guide` companion skill builds its whole indexing strategy on this flag.

**Gotcha:** the indexer does NOT execute JavaScript. A widget whose content arrives client-side (Vue/React data islands, AJAX loads) is invisible to search even without `NoOutput` - the index sees only the empty mount markup. Emit server-side HTML during index mode if that content must be findable.

### Routing: dynamic URL segments, marking them resolved, and page titles (verified 15.4)

Every segment after the page URL (`/news/detail/my-item`, `/reports/ForSession/{guid}/2027`) lands in `RouteData.Values["params"]` as a `string[]`, and Sitefinity starts every such request **presumed 404**: `PageRouteHandler.BuildHttpHandler` calls `RouteHelper.SetUrlParametersResolved(false)` whenever `Params` is present (true only for backend pages, or with `PagesConfig.EnableBackwardCompatabilityForPagesUrls`). At `PreRenderComplete` the same handler checks `RouteHelper.GetUrlParametersResolved()` and, if nothing on the page claimed the segments, sets `Response.StatusCode = 404` and ends the response - **after** your widget rendered. The flag is one boolean in `HttpContext.Items`, shared by every widget on the page: any one claiming the URL is enough. This is the mechanism behind "my detail page renders in the editor but 404s live".

**Who claims the segments for you (Feather `FeatherActionInvoker` + the params-mapper chain, `Telerik.Sitefinity.Frontend.Mvc.Infrastructure.Routing`):**

| Mechanism | What it matches | Marks resolved? |
|---|---|---|
| `[RelativeRoute("ForSession/{sessionId:guid}/{cohort}")]` on an action or controller (`Telerik.Sitefinity.Mvc`) | attribute routes relative to the page, via `RelativeDirectRouteProvider`; `AttributeRoutingManager.UpdateRouteData` copies the matched values into `RouteData` | **yes**, automatically when the route matches |
| `IRouteMapper.TryMapRouteParameters(string[] urlParams, RequestContext ctx)` implemented on the controller (`Telerik.Sitefinity.Frontend.Mvc.Infrastructure.Controllers`) | anything - you parse `urlParams` yourself and populate `ctx.RouteData.Values` | **yes**, when you return `true` (`DefaultUrlParamsMapper` calls `SetUrlParametersResolved` for you) |
| Convention dispatch (`MvcRequestContextBuilder.SetRouteParameters`) | `params[0]` = action name (case-insensitive, verb-filtered), `params[1..]` bound **positionally** to the action's parameters by declaration order | **yes, but only if** an action of that name exists **and** the segment count does not exceed its parameter count. Then `UrlParamsResolvedActionFilterAttribute` (registered globally) promotes the flag - unless the action returned `HttpNotFound()` |
| Stock content-widget mappers (`DetailActionParamsMapper`, `SuccessorsActionParamsMapper`, `TaxonomyUrlParamsMapper`, `DateUrlParamsMapper`, paging) | inferred from a `Details(T item)` action, taxonomy/date/page filters | yes, when an item/taxon/date matches |
| Manual: `RouteHelper.SetUrlParametersResolved()` (`Telerik.Sitefinity.Web`) | nothing - you decide | only when you call it |

So a plain `public ActionResult Detail(string urlName)` **already** works for `/page/Detail/some-url-name` with no attribute and no interface: the convention mapper binds `urlName` from the second segment and the filter marks the request resolved. The two ways it silently stops working: the URL has more segments than the action has parameters (404), or the action name is not the first segment (`/page/some-url-name` alone dispatches to `Index` with the segment unconsumed - 404). For URLs that are not `/{action}/{args}`-shaped, implement `IRouteMapper` or use `[RelativeRoute]`.

**Return `HttpNotFound()` for a missing item** rather than rendering an "empty" view: the global filter deliberately skips the resolved flag on `HttpNotFoundResult`, so the page becomes a true 404 instead of a 200 with an apology - the difference between search engines dropping a dead URL and indexing it. A WebForms-era detail control, or an MVC widget that resolves its own item outside the mapper chain, calls `RouteHelper.SetUrlParametersResolved()` directly once it has found the item (the stock `DynamicContentView`, `HierarchicalContentView`, `FormsMasterDetailView` and `RelatedDataViewExtensions` all do exactly this) and leaves the flag alone when it has not.

**Page title from a widget.** `ControllerActionInvoker.SetPageProperties` (`Telerik.Sitefinity.Mvc`) runs after your action, reads `ViewBag.Title` and, when non-empty, writes it to `Page.Header.Title` (the layout's empty `<title></title>` is filled by the WebForms page, not by Razor). That is the whole API for a custom widget:

```csharp
public ActionResult Detail(string urlName)
{
    var item = FindByUrlName(urlName);
    if (item == null) { return this.HttpNotFound(); }          // real 404, see above
    this.ViewBag.Title = $"{item.GetValue<string>("Title")} | {SiteMapBase.GetCurrentNode().Title}";
    return View("Detail", item);
}
```

Rules that follow from the code: the **last widget** on the page to set `ViewBag.Title` wins (each proxy overwrites `Page.Header.Title`); the value is written raw, so HTML-encode item titles you did not author; and if the controller also exposes a `MetadataFields` (`MetadataModel`) with `SEOEnabled && !SEOEnabledPerWidget`, `ViewBag.Title` is ignored in favour of the SEO path. `ViewBag.Title` is also what an `IPagePreRenderCompleteEvent` subscriber sees when it decorates every title site-wide (suffixing the site name, prefixing a dev marker) - do that once there instead of in every widget.

**The stock "SEO and OpenGraph" designer section** is what `ContentBaseController.MetadataFields` gives Feather content widgets: `MetadataModel { MetaTitle, MetaDescription, OpenGraphTitle/Description/Type/Image/Video, Url, SiteName, PageTitleMode, SEOEnabled, OpenGraphEnabled, *PerWidget }`. `InitializeMetadataDetailsViewBag(item)` fills `ViewBag.Metadata` from the item (`MetaTitle` falling back to `Title`, or the dynamic type's main short-text field), and `SetPageProperties` then applies `PageTitleMode`: `Replace` (default) uses the item title, `Append` gives `"{page} {item}"`, `Hierarchy` gives `"{item} - {parentMainField}"` for dynamic-content widgets, `DoNotSet` keeps the page title; `MetaDescription` and the `og:*` values become `<meta>` controls. Derive from `ContentBaseController` and call `InitializeMetadataDetailsViewBag` in your details action to get the section, its admin UI and consistent title behaviour for free; it does nothing in design mode. (The ASP.NET Core Renderer re-implements the same modes in `ContainerMetadataExtractor` - a different pipeline.)

## How widget properties ACTUALLY persist (verified platform behavior)

Public properties on the controller become designer fields. Understanding persistence prevents whole bug classes:

1. **Persistence is sparse via default-instance diffing.** On save, Sitefinity compares each property against a freshly constructed `new YourController()` and writes a database row ONLY for values that differ. Consequences:
   - A freshly dropped widget persists almost nothing - unset properties resolve from your C# defaults at runtime.
   - **Changing a property's C# default later retroactively changes every existing widget instance that was saved with the old default** - no row was ever written for it, so they all silently pick up the new default. Treat shipped defaults as a contract; if you must change one, audit existing instances first.
   - The `[DefaultValue]` attribute is NOT the persistence baseline (it seeds the designer UI); the C# property initializer is what the diff runs against.
2. **Values are invariant-culture strings** (`TypeConverter.ConvertToInvariantString`): "True", "42". Custom types need a TypeConverter that round-trips invariant strings.
3. **Complex types and lists MUST be marked `[PropertyPersistence(PersistAsJson = true)]`** (`Telerik.Sitefinity.Modules.Pages.PropertyPersisters`). The decompiled decision tree (`ObjectDataUtility.GetPersistenceType` + `PageHelper.IsSupportedComplexProperty`, 15.4):
   - `[Browsable(false)]` -> not persisted at all (except the `ControllerName` and `ID` key properties).
   - `PersistAsJson = true` on a `List<T>`, `IList<T>`, or any class -> **one JSON row** (`SitefinityPropertyPersister`, `JsonConvert.SerializeObject`). Deserialization failures are swallowed, so a type change that breaks JSON just yields the default value silently.
   - **Classes defined in `Progress.Sitefinity.Renderer.dll`** (`MixedContentContext`, `LinkModel`, `NumericRange`, `FileTypes`, ...) are JSON-persisted **automatically**, attribute or not (assembly-name regex in `PageHelper`). Adding the attribute is harmless and makes the intent explicit.
   - Otherwise: a type whose `TypeConverter` can convert from string -> one string row; a getter-only `IList`/`ICollection<T>` -> `ListPropertyPersister` (one `sf_object_data` row per item with per-property rows, and an item whose values all equal the item type's defaults produces ZERO rows and **silently vanishes on save**); a settable `IEnumerable` -> `EnumerablePropertyPersister`; an `IDictionary` -> `DictionaryPropertyPersister`; any other class with a properties-supporting converter -> `ComplexPropertyPersister` (nested rows).
   This is the #1 "my widget property doesn't stick" bug: mark every `IList<T>` of your own item classes `PersistAsJson = true`.

```csharp
using Telerik.Sitefinity.Modules.Pages.PropertyPersisters;

[PropertyPersistence(PersistAsJson = true)]
public List<FeatureItem> Features { get; set; } = new List<FeatureItem>();

[PropertyPersistence(PersistAsJson = true)]
public MixedContentContext HeroImage { get; set; }
```

4. `[Browsable(false)]` hides a property from the designer AND from persistence - use for computed/derived properties.

## Designer attributes: the working set (full reference in `sitefinity-designer-attributes`)

The complete attribute catalogue - every field type, every parameter, `KnownFieldTypes` values, what is MVC-only vs Core-only, and what has no server-side consumer - lives in **`sitefinity-designer-attributes`** (also served by the MCP server as the `sitefinity_widget_designer_attributes` resource). Load that skill when you are *designing* a property editor. This section is only the shape that covers ~90% of custom widgets, so a widget review does not need the whole reference in context:

```csharp
[ContentSection("Content", 0)] [DisplayName("Heading")] [Required] [DefaultValue("Build something")]
public string Heading { get; set; }

[ContentSection("Content", 1)] [DataType(customDataType: KnownFieldTypes.Html)]
public string Body { get; set; }                                   // rich text; TextArea, Color, Password, Range likewise

[ContentSection("Content", 2)] [DataType(customDataType: "linkSelector")]
public LinkModel PrimaryButton { get; set; }                       // one picker instead of text+url; null until configured

[ContentSection("Media", 0)]
[Content(Type = KnownContentTypes.Images, AllowMultipleItemsSelection = false)]
[PropertyPersistence(PersistAsJson = true)]                       // ALWAYS with MixedContentContext and IList<T>
public MixedContentContext HeroImage { get; set; }                // read with ManagerBase.GetItems(ctx, type)

[ContentSection("Items", 0)] [TableView(Reorderable = true, ColumnCount = 1)]
[PropertyPersistence(PersistAsJson = true)]
public IList<FeatureItem> Features { get; set; } = new List<FeatureItem>();   // [ContentSection(N)] on FeatureItem is 1-BASED

[ContentSection("Appearance", 0)] [DisplayName("Template")] [DefaultValue(MyTemplate.Centered)]
public MyTemplate Template { get; set; }                          // enum with [Description] members = dropdown

[ConditionalVisibility("{\"conditions\":[{\"fieldName\":\"Template\",\"operator\":\"Equals\",\"value\":\"Split\"}]}")]
public string SplitImageUrl { get; set; }

[Category(PropertyCategory.Advanced)] public string CssClass { get; set; }
[Browsable(false)] public string TemplateName => $"MyWidget.{this.Template}";   // derived, hidden, not persisted
```

Rules that bite, each expanded in the reference:

- **`[PropertyPersistence(PersistAsJson = true)]`** on every `MixedContentContext`, `IList<T>` and complex object - without it the value is flattened to `Property.Child` string pairs and selectors come back empty (see "How widget properties ACTUALLY persist" below).
- **`KnownFieldTypes` values are camelCase strings** (`"html"`, `"textArea"`, `"chipchoice"`); a wrong-cased raw string silently degrades to a text input. Use the constants.
- **`[ViewSelector]` only lists views under `ResourcePackages/{Theme}/MVC/Views/{Widget}/`** - with views in the project's `Mvc/Views/` the dropdown is empty. The enum-plus-derived-`TemplateName` pattern above is the reliable replacement.
- **`[ContentSection(N)]` inside a `[TableView]` item type is 1-based**; `0` floats to the end.
- **Core-Renderer-only, will not compile in MVC:** `[Copy]`, `[ContentContainer]`, `[ColorPalette]` (use `KnownFieldTypes.Color`, or a `[Choice]` list of brand colours).
- **Advisory only in 15.4 (no server-side consumer):** `[InitialValue]`, `[IsNullable]`.
- Namespaces: attributes in `Progress.Sitefinity.Renderer.Designers.Attributes` (`Progress.Sitefinity.Renderer.dll`), `[ConditionalVisibility]` for MVC in `Telerik.Sitefinity.Web.Services.PropertyEditor.Attributes`, `[ViewSelector]` in `Telerik.Sitefinity.Web.Services.Contracts.Operations.Pages.PropertyEditor.AttributeConfigurator.Attributes`.

## Dynamic links (`sfref`): how content references inside HTML are stored and resolved (verified 15.4)

Whenever an editor inserts an image, document, video, page link or content link into rich text, Sitefinity does **not** store the URL. It stores a **dynamic link**: an `sfref` attribute holding a provider-qualified key plus the item's GUID, and it re-resolves that key to a URL every time the HTML is rendered. That is what lets a URL rename, a media re-upload, a multisite move, or a blob-storage switch never break content. Verified from `Telerik.Sitefinity.Web.Utilities.LinkParser`, `Telerik.Sitefinity.Modules.GenericContent.DynamicLinksParser`, `Telerik.Sitefinity.Modules.HtmlFilterProvider`, the ContentBlock widget source, the property editor services, and real rows in a 15.4 database.

**Storage format** (what sits in `sf_control_properties.val` / `sf_content_items.content_` / any LongText field):

```html
<span class="sfImageWrapper" data-sfref="[images|OpenAccessDataProvider]4d2f4d28-892a-6afc-a007-ff0000973b9b">
  <img src="..." sfref="[images|OpenAccessDataProvider]4d2f4d28-..." alt="Litmos Logo" />
</span>
<a href="..." sfref="[documents|OpenAccessDataProvider]4d2e...">Policy PDF</a>
<a href="..." sfref="[pages]f669d9a7-...">About us</a>
<img sfref="[images|OpenAccessDataProvider|tmb:thumbnail]4d2e..." />        <!-- thumbnail profile option -->
```

The key grammar (`DynamicLinksParser.ParseDynamicLinkKey`): `[<key>|<provider>|<siteId>|<opt>:<val>...]<guid>` - segments split on `|`; segment 1 is the provider name, segment 2 (a Guid) the site id, and any `name:value` segment is an option (`tmb:` = thumbnail profile, `lng:` = language). `<key>` is `images` / `videos` / `documents` / `pages`, a full CLR type name (`Telerik.Sitefinity.DynamicTypes.Model.X.Y`, `Telerik.Sitefinity.News.Model.NewsItem`), or a page-node root GUID. The `href`/`src` next to it is a stale convenience copy the editor left behind; the `sfref` is the truth.

**Resolution** (`LinkParser.ResolveLinks(html, GetItemUrl itemUrl, ResolveUrl resolveUrl, bool preserveOriginalValue[, bool resolveAsAbsoluteUrl[, ProcessChunk]])`): walks the HTML with Sitefinity's `HtmlParser`, and for every `href`/`src`/`sfref` carrying a key calls the `GetItemUrl(string providerKey, Guid id, bool absolute, ContentLifecycleStatus status)` delegate. The stock delegate is **`DynamicLinksParser.GetContentUrl`**, which: for `images`/`videos`/`documents` resolves the media URL (respecting the `tmb:` profile, language, provider and site); for `pages` (or a root GUID) finds the sitemap node under `SiteRegion.FromSiteMapRoot` and returns its URL for the requested culture; for any other type resolves the manager via `ManagerBase.TryGetMappedManager`, loads the item inside `AllProvidersAccessRegion` + `ElevatedModeRegion`, asks `SystemManager.GetContentLocationService()` for the item's default location, and **registers the item as an output-cache dependency**. Unresolvable links become `#sf404` / `#Link.Not.Resolved#` (see `LinkParser.LinkNotResolvedBehaviour`). `preserveOriginalValue: true` keeps the `sfref` attribute next to the resolved `href` so the HTML can be unresolved again (`LinkParser.UnresolveLinks` works only on HTML resolved that way); `false` strips it for clean public output. Absolute vs relative follows `Config.Get<SystemConfig>().SiteUrlSettings.GenerateAbsoluteUrls` unless you pass it.

**Who resolves, and when** - this is the part that bites custom widgets:

| Path | Resolved by | Notes |
|---|---|---|
| Stock ContentBlock widget (`Telerik.Sitefinity.Frontend.ContentBlock`) | `ContentBlockModel`: `Content = LinkParser.ResolveLinks(content, DynamicLinksParser.GetContentUrl, null, SystemManager.IsInlineEditingMode)` | Also registers `OutputCacheDependencyHelper.GetPublishedContentCacheDependencyKeys(typeof(ContentItem), SharedContentID)` for shared blocks |
| Feather content widgets reading a LongText field through `ItemViewModel.Fields.X` | `HtmlFilterProvider.ApplyFilters` (`DynamicLinksParser` for the `sfContentFilters` set on the request, then the HTML sanitizer unless `SecurityConfig.DisableHtmlSanitization`) | **Returns `string.Empty` when there is no `SystemManager.CurrentHttpContext`** - a LongText read through `ItemViewModel` from a scheduled task or a background thread is silently blank |
| Backend property editor (AdminApp designer) | `WcfPropertyManager`: on **load** resolves with `preserveOriginalValue: true` (`ResolveLinks(text, DynamicLinksParser.GetContentUrl, null, true)`), on **save** runs `LinkParser.UnresolveLinks` - but only for properties marked **`[DynamicLinksContainer]`** | Same for inline editing (`PageControlStrategy`) |
| **Your own MVC widget property** holding HTML | **Nobody.** `MvcControllerProxy` does not touch property values at render; the raw `sfref` HTML reaches your view | Resolve it yourself (below). A view that emits `@Html.Raw(Model.Content)` unresolved renders the editor's stale `src` - it works until the media moves, then breaks |

So `[DynamicLinksContainer]` (namespace `Telerik.Sitefinity.Modules.GenericContent`, marker only) does **two** things and neither is render-time: it makes the designer round-trip the HTML (resolve on load with `sfref` preserved, unresolve on save so GUID keys, not URLs, get persisted), and it flags the property as link-bearing for inline editing. Put it on every string property that holds rich text. Without it, a designer save persists whatever URLs the editor's HTML happened to contain.

**Resolving in your own code** - the production idiom (a `Html.Raw` overload that resolves), verified against the parser:

```csharp
using Telerik.Sitefinity.Modules.GenericContent;   // DynamicLinksParser
using Telerik.Sitefinity.Web.Utilities;            // LinkParser

// Public rendering: resolve, strip sfref, relative URLs
public static IHtmlString Raw(this HtmlHelper helper, object html, bool resolveContent)
{
    var content = resolveContent
        ? LinkParser.ResolveLinks(html.ToString(), DynamicLinksParser.GetContentUrl, null, false)
        : html.ToString();
    return new MvcHtmlString(content);
}

// Exports / emails / JSON for a JS island: absolute URLs
var abs = LinkParser.ResolveLinks(html, DynamicLinksParser.GetContentUrl, null, false, resolveAsAbsoluteUrl: true);

// HTML that came back from the backend/inline editor already resolved WITH sfref preserved:
// unresolve first, then resolve for the current context (otherwise stale hrefs win)
var clean = LinkParser.ResolveLinks(LinkParser.UnresolveLinks(html), DynamicLinksParser.GetContentUrl, null, false);

// Cheap pre-check
if (LinkParser.ContainsDynamicLinks(html)) { ... }

// Resolve one key yourself (e.g. a data-sfref you pulled out of the markup)
string url = DynamicLinksParser.GetContentUrl("[images|OpenAccessDataProvider|tmb:thumbnail]", id, resolveAsAbsoluteUrl: false, ContentLifecycleStatus.Live);
```

Rules that follow:

- **Never persist resolved HTML.** Store what the editor gave you (with `sfref`), resolve at render. If you generate HTML in code that references media, write `sfref` keys, not URLs.
- **Never parse `sfref` with your own regex to look up items** when a URL is what you need - `GetContentUrl` handles provider, culture, site, thumbnail profile, lifecycle status and cache dependencies. Use `LinkParser.TryExtractValues(Uri, out IDictionary<string, object>)` / `TryGetImageId(...)` when you genuinely need the id.
- **Resolve with the lifecycle status of the page you are on.** `GetContentUrl` takes a `ContentLifecycleStatus`; the stock filters pass Live on the public site and the draft parser in the backend (`sfContentFilters` = `DraftLinksParser`, which is `new DynamicLinksParser(preserveOriginalValue: true)`).
- **Outside a request** (scheduled tasks, startup code) `HtmlFilterProvider.ApplyFilters` returns empty and `GetContentUrl` needs a site context - wrap in `SiteRegion.FromSiteId(...)` / `CultureRegion` and call `LinkParser.ResolveLinks` directly instead of going through `ItemViewModel`.
- **Related-data fields are not dynamic links.** `sf_content_link` rows (RelatedData / RelatedMedia fields) are a separate, structured mechanism resolved through `GetRelatedItems` - see `sitefinity-api-helpers` and `sitefinity-database-structure`. Dynamic links live *inside* HTML strings; related data lives in link rows. A content block's inline image is the former; a "Featured image" field is the latter.

## ItemViewModel: the dynamic view model Feather content widgets hand to views (verified 15.4)

Every built-in Feather content widget (News, Dynamic content, Lists, Media, ...) and every custom widget built on `ContentModelBase` renders **`Telerik.Sitefinity.Frontend.Mvc.Models.ItemViewModel`**, not the raw data item. It is a thin, `dynamic`-backed wrapper that lets one view template serve any content type. It is the most-used type in a mature site's views (the reference site has 140 references and reads `Model.Fields.Title` 111 times), so know exactly what it does.

```
ContentModelBase (your model, or the stock one)
  GetItemsQuery()  -> IQueryable<IDataItem>
  CreateListViewModel(...)    -> ContentListViewModel   { IEnumerable<ItemViewModel> Items, ContentType, ProviderName, CssClass, UrlKeyPrefix, TotalPagesCount, CurrentPage, ShowPager }
  CreateDetailsViewModel(item)-> ContentDetailsViewModel { ItemViewModel Item, ContentType, ProviderName, CssClass, EnableSocialSharing }
  CreateItemViewModelInstance(item) -> new ItemViewModel(item)   // virtual: override to return a subclass
```

**The shape** (decompiled):

| Member | What it is |
|---|---|
| `IDataItem DataItem` | The underlying item (`NewsItem`, `DynamicContent`, `Image`, ...). Cast it when you need the strongly typed API |
| `dynamic Fields` | A `DynamicDataItemFieldAccessor` (`DynamicObject`). `Model.Fields.Title`, `Model.Fields.MyCustomField` resolve **at runtime** through `TypeDescriptor.GetProperties(DataItem)[name]` - which is why custom Module Builder fields work without a C# class |
| `string DefaultUrl` | `DataItem.GetDefaultUrl()` - the item's canonical URL |
| `object Identifier` | The value of the type's "identifier" field (`RelatedDataHelper.GetRelatedTypeIdentifierField`, normally `Title`) |
| `IEnumerable<ItemViewModel> RelatedItems(string fieldName)` / `ItemViewModel RelatedItem(string fieldName)` | Related-data fields resolved via `GetRelatedItems(fieldName)`, wrapped again as `ItemViewModel`, cached per instance, and registered as output-cache dependencies |
| `IList<FlatTaxon> GetFlatTaxons(fieldName)`, `GetFlatTaxon(fieldName)`, `IList<HierarchicalTaxon> GetHierarchicalTaxons(fieldName)`, `GetHierarchicalTaxon(fieldName)` | Taxonomy fields as taxon objects (via `TaxonomyApplicationState`, cached) |
| `string GetDateTime(string fieldName, string format)` | **Converts through `ToSitefinityUITime()`** before formatting - this is the built-in way to show dates in the site's UI time zone; returns `null` for `default(DateTime)` |
| `string GetBool(fieldName)` | Localized "Yes"/"No" |
| `string GetMultipleChoiceValueString(fieldName)` | Comma-joined choices |
| `string GetPrice(fieldName, format)`, `string GetAddressString(fieldName, format)` (`#=Street#`, `#=City#`, `#=Zip#`, `#=State#`, `#=Country#` tokens) | Formatting helpers |
| `string SerializeToJson(fieldName)` | `JavaScriptSerializer` JSON of a field value |

**What `Fields.X` actually returns** (`DynamicDataItemFieldAccessor.GetMemberValue`) - the part people get wrong:

- A **related-data field** (`RelatedDataPropertyDescriptor`) does NOT return ids or `IDataItem`s: it returns `RelatedItems(name)` (an `IEnumerable<ItemViewModel>`, materialized as an array) when the field allows multiple relations, or `RelatedItem(name)` (a single `ItemViewModel` or `null`) otherwise. So `Model.Fields.Images` is a list of `ItemViewModel`s whose own `.Fields.MediaUrl` / `.Fields.ThumbnailUrl` / `.Fields.AlternativeText` you read in the same way, and `Model.Fields.Author.Fields.Title` walks one level deeper. `.Length` / `.FirstOrDefault()` work because it is an array.
- A **LongText** field (`UserFriendlyDataType.LongText`) is returned as a `string` run through `HtmlFilterProvider.ApplyFilters` (dynamic-link resolution, sanitizer) - unless the item implements `IDeferredHtmlFilterContainer`, in which case filtering is deferred to render time. Everything else comes back as the raw property value (`Lstring` for text, `DateTime`, `decimal?`, `TrackedList<Guid>` for taxonomies, `Address`, `Guid`, ...).
- A **Link** field returns the link JSON with `sfref` links resolved to real `href`s.
- An unknown name returns `null` and the `dynamic` binder reports the member as missing, so `Model.Fields.Typo` throws `RuntimeBinderException` at render time - not at compile time. Field names are case-sensitive property names.
- Because `Fields` is `dynamic`, Razor helpers that take `object`/`string` need a cast: `((string)Model.Fields.Title).TruncateString(50, ...)`, `(ItemViewModel[])Model.Fields.Documents`.

```razor
@model Telerik.Sitefinity.Frontend.Mvc.Models.ItemViewModel
@using Telerik.Sitefinity.Frontend.Mvc.Models;

<h2><a href="@Model.DefaultUrl">@Model.Fields.Title</a></h2>
<time>@Model.GetDateTime("PublicationDate", "MMM d, yyyy")</time>      @* UI time zone, not server time *@
@Html.Raw(Model.Fields.Content)                                           @* LongText: already HTML-filtered *@

@foreach (var tag in Model.GetFlatTaxons("Tags")) { <span>@tag.Title</span> }

@foreach (var img in Model.Fields.Images)                                 @* related media = ItemViewModel[] *@
{
    <img src="@img.Fields.ThumbnailUrl" alt="@img.Fields.AlternativeText" />
}

@{ var author = Model.RelatedItem("Author"); }
@if (author != null) { <p>@author.Fields.Title</p> }

@{ var typed = Model.DataItem as Telerik.Sitefinity.DynamicModules.Model.DynamicContent; }   @* drop to the real item when you need the API *@
```

**Where it is created.** `ContentModelBase.CreateItemViewModelInstance(IDataItem)` is `protected virtual`; override it in your model to return an `ItemViewModel` subclass with typed convenience properties (keep `Fields` for the generic case). `ContentModelBase` also owns the list/detail pipeline you inherit for free: `SelectionMode`, `FilterExpression` / `SerializedAdditionalFilters` / `SerializedDateFilters`, `SortExpression`, `ItemsPerPage` / `LimitCount`, `DisplayMode`, related-item mode (`RelatedItemType`, `RelatedFieldName`, `RelationTypeToDisplay`), `CreateListViewModel(ITaxon taxonFilter, int page)`, `CreateListViewModelByRelatedItem(IDataItem relatedItem, int page)`, `CreateListViewModelByDate(DateTime from, DateTime to, int page)`, `GetKeysOfDependentObjects(...)` for output-cache invalidation.

**Capabilities most sites leave on the table.** Measured on the reference site (140 `ItemViewModel` references, ~30 custom content widgets): it reads `Fields.*` everywhere and calls `GetDateTime` a dozen times, `GetFlatTaxons` / `GetHierarchicalTaxons` three times each, and uses `ShowPager` / `TotalPagesCount` / `UrlKeyPrefix` / `SelectionMode` / `SerializedAdditionalFilters` from the stock list model. Everything below is **verified to exist and unused there** - each replaces code that sites typically hand-roll:

- `Model.DefaultUrl` - the canonical detail URL through the URL system (multisite-, culture- and provider-aware). Sites usually rebuild it from `UrlName` and a hard-coded page path.
- `RelatedItem(field)` / `RelatedItems(field)` called explicitly (rather than through `Fields.X`) when you need the `ItemViewModel` wrapper without the dynamic binder, e.g. from a typed helper, and they register the related items as **output-cache dependencies** for free - a hand-written `GetRelatedItems` in a controller does not, so the cached page goes stale when the related image changes.
- `GetFlatTaxon(field)` / `GetHierarchicalTaxon(field)` - first-taxon shortcuts; `HierarchicalTaxon` gives you `.Parent` and `.FullUrl` for breadcrumbs.
- `GetBool(field)` - localized Yes/No through Sitefinity's label resources (respects backend language packs).
- `GetMultipleChoiceValueString(field)` - joined multiple-choice values without a `string.Join` over a `TrackedList`.
- `GetAddressString(field, "#=Street# #=City#, #=State# #=Zip# #=Country#")` - Address fields with country/state names resolved from `LocationsConfig`.
- `SerializeToJson(field)` - a field as JSON for a data island (but see the downsides).
- `Identifier` - the type's identifier field without knowing whether it is `Title`, `Name`, or something else.
- **`ContentModelBase` itself** - zero uses on the reference site, whose widgets query `GetDataItems` by hand. Inheriting it gives the stock designer's selection modes (all / selected items / by parent / by taxon / by date / by related item), the compiled filter + sort expressions, paging, `CreateListViewModelByRelatedItem` / `ByDate`, `IContentLocatableView.GetLocations()` (so the backend "content locations" and canonical-URL meta tags know the widget hosts this type), and `GetKeysOfDependentObjects` (correct output-cache invalidation) - roughly the half of every custom list widget that is not the markup. Override `GetItemsQuery()` for the query and `CreateItemViewModelInstance()` for a typed wrapper; keep the rest.

**Downsides, clearly** (all from the decompiled implementation):

1. **No compile-time safety.** `Fields` is `dynamic`: a misspelled or removed field throws `RuntimeBinderException` when the view renders, and Razor IntelliSense is blind. Every `Model.Fields.X` also pays a `TypeDescriptor.GetProperties(DataItem)[name]` reflection lookup; plain field reads are **not** cached (only the helper methods cache per instance).
2. **Nullable unboxing bugs.** `GetDateTime` does `(DateTime)Fields.GetMemberValue(name)` and `GetBool` does `(bool)...` - a `DateTime?` / `bool?` field that is empty throws `NullReferenceException` at render time. Guard with `Model.Fields.X != null` first, or read the nullable through `Fields` and format yourself.
3. **N+1 queries on lists.** `RelatedItems` / `RelatedItem` (and therefore `Fields.SomeRelatedField`) run `GetRelatedItems` **per item**; a 50-item list touching two related fields is 100+ queries. The per-instance cache only saves repeat reads on the same item. For list views, resolve related items in the model in one query and pass them in, or accept the cost for small pages.
4. **LongText is filtered on every read.** Each access of a LongText field runs `HtmlFilterProvider.ApplyFilters` (dynamic-link resolution and sanitization) unless the item is an `IDeferredHtmlFilterContainer`; reading `Fields.Content` twice filters twice. Read it once into a local.
5. **Lifecycle follows the item you wrap.** Wrapping a Master item resolves master-scoped related items and unpublished data; wrap Live items (`Status == Live && Visible`) for anything public.
6. **Legacy serializer.** `SerializeToJson` uses `System.Web.Script.Serialization.JavaScriptSerializer` (WCF-style `\/Date(...)\/` for dates, no camelCase, no `[JsonProperty]` support). For JS consumers, build a DTO and use `ServiceStack.Text` / Newtonsoft as the rest of the site does.
7. **`Fields` cannot leave Razor.** A `DynamicObject` does not round-trip through JSON serializers or view-model caches; it is a render-time convenience only.
8. **Hidden coupling to designer conventions.** `Identifier` depends on `RelatedDataHelper`'s notion of the identifier field, and `Fields.X` for Link fields returns *JSON text* (resolved `sfref`s) rather than a `LinkModel` - both surprise people the first time.

**When to use it vs a POCO.** `ItemViewModel` is the right model for Razor views that Sitefinity's stock widgets, designer "template" selectors, and content editors expect (one template, any type, reads a custom field the day it is added). A strongly typed POCO (`sitefinity-poco-generator`) is the right model when the data leaves Razor - JSON for a Vue/React island, a ServiceStack DTO, a scheduled task - because `dynamic` does not serialize predictably and the hydration cost (related items, taxa) should happen once, explicitly, on Live items. Do not pass `ItemViewModel` through `JsonSerializer`.

## Toolbox icons: `CssClass` on `[ControllerToolboxItem]`

Icon CSS classes for the toolbox tile come from Sitefinity's built-in backend sprite sheet - no new assets required.

### Usage

Set `CssClass` to **two** classes: the specific icon class first, then
`sfMvcIcn` (which paints the blue "MVC" badge on the tile).

```csharp
[ControllerToolboxItem(
    Name = "MyStats_MVC",
    Title = "Stats",
    SectionName = "ContentToolboxSection",
    CssClass = "sfStatisticsIcn sfMvcIcn")]
public class MyStatsController : Controller
{
    // ...
}
```

Order doesn't matter functionally, but putting the icon first matches
Sitefinity's own convention (e.g. `sfNavigationIcn sfMvcIcn` on the
Navigation widget).

Without a specific icon class, the tile renders blank (just the MVC
badge on an empty square).

### Tracking your own assignments

Keep a table of which icon class each of your widgets uses in your own
project documentation. Since the sprite sheet is shared, tracking your
assignments makes it easy to pick an unused icon that best matches a new
widget's purpose and avoids two widgets colliding on the same tile.

### Badging MVC widgets in the page editor (WebForms -> MVC migrations)

`sfMvcIcn` only badges the TOOLBOX tile. To also badge each widget already
ON the page, add this CSS to any stylesheet that loads inside the page
editor (a backend theme stylesheet, or a globally loaded frontend CSS -
everything is scoped under `.sfPageEditor`, so it is a silent no-op on
public pages):

```css
.sfPageEditor #sfPageContainer div[controltype^="Telerik.Sitefinity.Mvc"] .rdCenter .rdTitleBar>em:after,
.sfPageEditor #sfPageContainer div[controltype^="Telerik.Sitefinity.Frontend.Mvc"] .rdCenter .rdTitleBar>em:after {
    content: "MVC";
    background-color: #105cb6;
    color: #fff;
    font-size: 10px;
    padding: 0 4px;
    margin-left: 5px;
}
```

What it does: every widget's RadDock title bar in the zone editor gets a
small blue "MVC" tag when the widget is MVC-based. The `controltype`
attribute on the editor's widget wrapper carries the control's .NET type,
so the two prefix selectors catch both flavors:

- `Telerik.Sitefinity.Mvc` -> classic MVC widgets (`MvcControllerProxy` -
  i.e. all your custom controllers)
- `Telerik.Sitefinity.Frontend.Mvc` -> Feather dynamic widgets
  (`MvcWidgetProxy`)

Why bother: during a WebForms -> MVC migration you can open any page in
the editor and see at a glance which widgets are migrated (badged) and
which are legacy WebForms (unbadged) - no clicking into each widget. It
also just looks nice.
